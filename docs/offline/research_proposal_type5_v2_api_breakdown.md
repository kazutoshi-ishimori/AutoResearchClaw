## 2. 用途 A：生成物品質チェック（約 1 万円）

### 2.1 何をしているか

AutoResearchClaw（ARC）が出力する**論文ドラフト 1 本**について、Claude に「査読者・編集者」役を演じさせ、以下を自動チェックする：

1. **数値整合性**：Abstract に出てくる数値（"accuracy 0.87"、"n=395" 等）が、Results / 図表内の数値と一致しているか
2. **用語統一**：本文中で同一概念に複数表記（例：「DTI」「Drug-Target Interaction」「ドラッグ標的相互作用」の混在）がないか
3. **過剰主張の検出**：「world-first」「outperforms all baselines」「completely solves」など、エビデンス不足の強い表現を抽出
4. **引用妥当性**：本文中の `[Smith2024]` が citations.bib に存在するか、引用元の主張と本文の言い回しが整合するか
5. **IMRAD 構造整合**：Introduction で立てた問いが Conclusion で回収されているか、Methods で書いた手法が Results に対応しているか
6. **指示語の解像度**：「これにより」「上記の通り」が何を指しているか曖昧でないか

→ ARC の `paper_v2_build` 後段、もしくは投稿前の最終仕上げ段で、人手レビュー前の「下処理」として実行する用途。

### 2.2 トークンの内訳

**1 論文あたりの入力**：

| 入力素材 | 推定 token 数 |
|---|---|
| paper_draft.md（IMRAD 全体、6,000〜10,000 word） | 約 15,000 |
| paper_v2.tex（最終版があれば） | 約 20,000 |
| experiment_results.json | 約 5,000 |
| draft_quality.json | 約 3,000 |
| hypothesis.json + experiment_plan.json | 約 5,000 |
| citations.bib | 約 10,000 |
| プロンプト指示文（査読視点、チェック観点リスト） | 約 2,000 |
| 余裕 | 約 5,000 |
| **小計（1 論文）** | **約 65,000 token ≒ 0.065 Mtok** |

ただし**システムプロンプトキャッシュなし・複数観点を並行してチェック**するため、観点ごとに分けて投入すると同じ入力を 5〜10 回読み返す。Claude のプロンプトキャッシュを使えば 2 回目以降は 10% 価格で済むが、安全側で **1 論文 0.5 Mtok / 入力**として見積もる。

**1 論文あたりの出力**：修正提案リスト（コメント・置換案）約 5,000 token = 0.005 Mtok → 0.05 Mtok と多めに見積もり。

**件数の根拠**：
- 半年で ARC を月 5 ラン × 6 ヶ月 = **30 ラン**
- 全ランで paper を生成しないため、品質チェック対象は実質 20〜30 本
- 試行錯誤分込みで **30 件**で見積もり

**合計**：30 件 × (input 0.5 Mtok / output 0.05 Mtok) = input 15 Mtok / output 1.5 Mtok

**金額**：
- input 15 Mtok × $3/Mtok = $45
- output 1.5 Mtok × $15/Mtok = $22.5
- 合計 $67.5 ≈ **約 1 万円**

### 2.3 何が支配的か

入力トークンが支配的。**論文 1 本につき複数ファイルを読ませる構造**のため、ドラフト 1 本あたりの料金が「単純な行数 × 価格」より一桁多くなる。プロンプトキャッシュを正しく使えば実コストは半額以下に抑えられる可能性あり。

## 3. 用途 B：ARC ログ解析・改善点提示（約 18 万円）

### 3.1 何をしているか

ARC を 1 ラン回した後、以下のような疑問に Claude に答えてもらう：

1. **どのステージで何が失敗したか**：23 ステージのうち、quality_warning / degraded:true / max_pivots_reached / All models failed 等のフラグが立ったステージを列挙し、根因を推測
2. **lessons.jsonl の共通パターン抽出**：複数ランの lessons を横断して「いつも同じステージで同じ失敗をしている」パターンを発見
3. **プロンプト改善提案**：失敗ステージのプロンプトを読み、「ここに制約を追加すべき」「フォールバック条件をこう変えるべき」といった具体案を出す
4. **新スキル候補の抽出**：`.claude/skills/arc-*` として永続化すべき知見を lessons から抽出
5. **モデル割り当ての見直し**：どのステージで Opus が必要か／Sonnet で済むか／Haiku でも動くか、を実測ログから推定
6. **ablation の差分検出**：experiment_diagnosis.json から identical_conditions 等の構造欠陥を早期発見

→ つまり、**ARC を「改善し続けるための運用知能」を Claude に肩代わりさせる用途**。本研究の方法論論文には「ARC 改善ループ」自体は載らないが、研究遂行上は必須の作業。

### 3.2 トークンの内訳

**1 ラン分の入力**：

| 入力素材 | 推定 token 数 |
|---|---|
| pipeline_summary.json | 約 5,000 |
| 各 stage の output.json（23 ステージ） | 約 1,500,000 |
| lessons.jsonl | 約 50,000 |
| draft_quality.json / experiment_diagnosis.json 等 | 約 20,000 |
| 各ステージのプロンプト・レスポンス抜粋 | 約 3,000,000 |
| 過去ランとの比較用に複数ランを横並べ | 約 500,000 |
| プロンプト指示文（解析観点・出力フォーマット） | 約 10,000 |
| **小計（1 ラン、フル投入時）** | **約 5,000,000 token ≒ 5 Mtok** |

実際にはランごとに**全ステージのプロンプト・レスポンスをまるごと**入れるのは過剰なので、quality_warning 等が立ったステージ周辺だけ抽出する場合は 1〜2 Mtok まで圧縮可能。ただし「網羅的な根因解析」を目的とする回もあるため、**安全側で 1 ラン 5 Mtok**で見積もる。

**1 ラン分の出力**：改善提案レポート（マークダウン構造、各ステージごとの所見＋具体的な修正案）約 30,000 token = 0.03 Mtok → 余裕を見て 0.3 Mtok。

**件数の根拠**：
- 半年で ARC を月 10 ラン × 6 ヶ月 = **60 ラン**
- 全ランでログ解析をかける（毎ラン後に「次に何を直すべきか」を Claude に問う）
- 試行錯誤・複数ラン横断の比較解析を含めて **60 ラン**で見積もり

**合計**：60 ラン × (input 5 Mtok / output 0.3 Mtok) = input 300 Mtok / output 18 Mtok

**金額**：
- input 300 Mtok × $3/Mtok = $900
- output 18 Mtok × $15/Mtok = $270
- 合計 $1,170 ≈ **約 18 万円**

### 3.3 何が支配的か

**入力トークン量が圧倒的に支配的**（$900 / $1,170 = 77%）。ARC のステージごとのプロンプト＋レスポンス＋中間出力をまるごと投入する構造のため、1 ラン 5 Mtok という大きな数字になる。
プロンプトキャッシュで「ベースの過去ランログ」を再利用すれば実質コストは半額前後に抑えられる余地あり。

## 4. 用途 C：Opus 利用・試行錯誤・再実行余裕分（10〜30 万円）

### 4.1 何をしているか

1. **本研究の方法論論文の最終仕上げ**：Discussion / Limitations の文体調整、共著者コメントの統合、Reviewer 反論レビュー（ストレッチ目標時）
2. **特に重い解析タスク**：Stage 18 PEER_REVIEW の代替実行、複数論文・複数ランの横断比較
3. **試行錯誤のやり直し**：プロンプト調整中に同じ入力を何度も投入する分

### 4.2 トークン感（Opus 4.7 は Sonnet の 5 倍価格）

- Opus 4.7：input $15/Mtok、output $75/Mtok
- 用途 A・B の **1〜3 割を Opus に置き換え**たケースで試算：
  - 仮に用途 B の 2 割（input 60 Mtok / output 4 Mtok）を Opus 化：
    - 60 × $15 + 4 × $75 = $900 + $300 = $1,200 ≈ 約 18 万円（Sonnet 比 +12 万円）
  - 試行錯誤・複数案比較で同じ入力を 1.5 倍流したケース：上記の 1.5 倍 = 約 27 万円

→ **10〜30 万円の幅**は、Opus 利用度合いと試行錯誤の量で決まる。

## 5. サブスク代替可能性の検討

旦那様のご質問の本丸。**API の従量課金ではなく、月額サブスクで済むか**を検討します。

### 5.1 各プランの月額・特徴（2026 年 4 月時点の公開情報）

| プラン | 月額 | 主な制限 | プログラマブル？ |
|---|---|---|---|
| **Claude Pro** | $20（約 3,000 円） | 5 時間ローリングで Pro の 5x（Max 5x の 1/5） | × チャット UI のみ |
| **Claude Max 5x** | $100（約 15,000 円） | 5 時間ローリングで Pro の 5 倍メッセージ | × チャット UI のみ |
| **Claude Max 20x** | $200（約 30,000 円） | 5 時間ローリングで Pro の 20 倍メッセージ | × チャット UI のみ（Claude Code 経由は可） |
| **ChatGPT Plus** | $20（約 3,000 円） | GPT-5.4 にレートリミットあり、長文制約 | × UI のみ（GPT Pro Mode あり） |
| **ChatGPT Pro** | $200（約 30,000 円） | GPT-5.4 Pro Mode、Sora 等にアクセス | × UI のみ |
| **Sonnet 4.6 API 従量** | 使った分（input $3/output $15 per Mtok） | レートリミットあり、課金は実トークン | ◎ 完全プログラマブル |
| **Opus 4.7 API 従量** | 使った分（input $15/output $75 per Mtok） | 同上 | ◎ |

### 5.2 各用途で代替可能か

| 用途 | サブスクで代替可？ | 推奨 |
|---|---|---|
| A. 生成物品質チェック（月 5 本程度） | **Claude Max 5x で十分可能**。チャットに paper_draft.md ＋ JSON 添付して観点ごとに対話 | Max 5x（$100/月） |
| B. ARC ログ解析（月 10 ラン × 1 ラン 5 Mtok） | **厳しい**。1 ラン 5 Mtok を会話 UI に投入できる枠は Max 20x でも 5 時間あたり 1〜2 回が限界、月 10 ランは不可能ではないが操作の手間が膨大。**プログラマブル投入が前提なので API が現実的** | API |
| C. Opus 仕上げ・査読 | **Claude Max 20x で可能**（Opus にもアクセス可、5 時間あたり数回） | Max 20x（$200/月） |

### 5.3 サブスクの制約（要注意）

1. **5 時間ローリングウィンドウ**：Claude Max は「5 時間あたり N メッセージ」の制限。深夜にまとめて作業する用途には向くが、CI / 自動実行は不可
2. **fair use 制限**：Max 20x でも 1 アカウントで連続的に大量入力すると一時停止される
3. **API キー発行不可**：プログラム経由の自動投入は不可（Claude Code 経由なら可能だが、それは別経路）
4. **長文の途中切断**：1 メッセージあたりの入力上限（およそ 200K tokens）を超えると切り詰めが発生
5. **会話履歴の累積**：1 会話あたりのコンテキストウィンドウを使い切ると新規会話が必要

### 5.4 研究費（科研費）との関係

- **個人購読のサブスクは研究費から出せない可能性が高い**：会計上、定額の個人購読サービスは「研究設備」「消耗品」「役務費」のいずれにも区分しづらく、機関側ルールで NG となるケースが多い。学内事務に要確認
- **API の従量課金は研究費から出せる**：「クラウドサービス利用料」「データ解析役務費」等で計上可能（機関の運用ルール次第）
- → **個人購読は私費、API のみ研究費**、というハイブリッド構成が現実的

## 6. 予算圧縮の現実的な選択肢

### 6.1 案 X：申請書通り API 主体（30〜50 万円）

**メリット**：プログラマブル自動化（CI 統合、夜間バッチ可、複数ラン横断比較が容易）
**デメリット**：金額が出る
**向き**：研究費から API を出せる場合の本命

### 6.2 案 Y：ハイブリッド（私費 Max 20x ＋ 研究費 API 5〜10 万円）

**構成**：
- 個人購読：Claude Max 20x ($200/月 ≒ 30,000 円/月 × 6 ヶ月 = 18 万円、**私費**)
  - 用途 A（生成物品質チェック）を全面カバー
  - 用途 C（Opus 仕上げ）を概ねカバー
- 研究費 API（5〜10 万円）：
  - 用途 B（ARC ログ解析）を Sonnet API で必要最小限実施
  - 投入を「失敗ステージ周辺のログ抽出のみ」に限定すれば、1 ラン 1 Mtok まで圧縮可能 → 月 10 ラン × 1 Mtok = input 10 Mtok / 月、6 ヶ月で 60 Mtok = $180 = 約 3 万円
  - Opus 補助で +2〜7 万円

**メリット**：研究費の API 計上は 5〜10 万円に圧縮できる
**デメリット**：旦那様の私費負担が 18 万円、用途 B が手動寄りになる
**向き**：研究費でサブスクが出せない＆私費負担を許容できる場合

### 6.3 案 Z：API 課金を強く圧縮（10〜15 万円）

**構成**：
- 用途 A：プロンプトキャッシュ徹底＋観点を 1 回投入にまとめて、1 論文 0.2 Mtok まで圧縮 → 30 件で input 6 Mtok / output 1 Mtok ≈ 6,000 円
- 用途 B：失敗ステージ周辺のみ投入 1 ラン 1 Mtok まで圧縮 → 60 ラン × 1 Mtok = 60 Mtok / output 5 Mtok ≈ 30,000 円
- 用途 C：Opus 利用を最低限（Discussion 仕上げのみ）→ 3〜5 万円

**合計**：約 4 万円 + α = **10〜15 万円**
**メリット**：API のみで完結、自動化可能、研究費でフル計上可能
**デメリット**：用途 B の網羅性が落ちる（全ステージログ横断解析は不可）
**向き**：API のみで予算を抑えたい場合

## 7. 推奨

**研究費の運用ルール次第**ですが、以下を推奨します：

| シナリオ | 推奨案 |
|---|---|
| 研究費から API 課金がフルで出せる（最も自由度高い） | **案 X（30〜50 万円、申請書通り）** |
| 研究費からサブスクは出せないが API は出せる、私費は許容 | **案 Y（私費 Max 20x 18 万円 + 研究費 API 5〜10 万円）** |
| 研究費の API 計上を強く圧縮したい | **案 Z（10〜15 万円、運用負荷増を許容）** |

実務的には、**案 Y のハイブリッド**が「日常開発の生産性は Max 20x で確保、研究の自動化部分だけ API」とバランスが取れていて現実的です。

### 7.1 申請書本体への反映方針

旦那様の方針確定後、次のいずれかで申請書 7.2 を書き換えます：

- **案 X 維持**：現状の 30〜50 万円のまま、注記として「プロンプトキャッシュ徹底で圧縮余地あり」を補足
- **案 Y 採用**：API 予算を 5〜10 万円に圧縮、注記として「定額サブスクは個人購読として研究費外で対応」と明示（または記載省略）
- **案 Z 採用**：API 予算を 10〜15 万円に圧縮、用途定義を「失敗ステージ周辺のログ解析」に限定

## 8. 補足：トークン経済の超圧縮テクニック

API 課金を抑えたい場合、以下を組み合わせると **実コストを 5〜7 割に削減**できる可能性があります：

1. **プロンプトキャッシュ**（Anthropic）：同じシステムプロンプト・同じドキュメントを 5 分以内に再利用する場合、キャッシュヒット部は 10% 価格（output は変わらず）
2. **入力の選別**：ARC ログから「失敗マーカー（quality_warning、All models failed 等）の周辺 500 行のみ」を抽出して投入
3. **観点の集約**：用途 A の 6 観点を 1 プロンプトに集約し、複数回投入を回避
4. **Sonnet → Haiku 切替**：ルーチンチェックは Haiku 4.5（Sonnet の 1/5〜1/4 価格）で十分
5. **バッチ API**：応答時間が許容できる用途は Batch API（半額）

これらを徹底すれば、案 X でも実コストは 15〜25 万円に収まる可能性があります。

1. 案 X / Y / Z のいずれを軸に申請書 7.2 を書き換えるか
2. 案 Y を採用する場合、私費 Max 20x（$200/月 × 6 = 18 万円）の負担を許容できるか
3. 案 Z を採用する場合、「用途 B の網羅性低下」を許容できるか（半年で実用上は問題ない見立てですが、改善ループの速度はやや落ちます）
4. 機関側で**サブスクは研究費から出せるか／API のみか**——大沼先生もしくは事務確認が必要です
