# AutoResearchClaw 閉域版 要件定義書

- **作成日**: 2026-04-15
- **対象**: AutoResearchClaw v0.4.0 以降を、個人情報を含む機微データ（例: 東北メディカル・メガバンク dbTMM の全ゲノム/MRI/マイクロバイオーム/コホートデータ）を扱う閉域環境で運用するための要件整理
- **ステータス**: Draft（Phase 0 — 未記入項目は運用側で確認のうえ埋める）

---

## 1. 背景と目的

### 1.1 背景
- 大学研究室にて AutoResearchClaw を用いた自動論文生成ワークフローを運用したい。
- 扱うデータ（例: dbTMM）は個人を再識別しうる機微情報であり、分譲先の**閉域解析環境**からの持ち出しが禁じられている。
- 既存の AutoResearchClaw は LLM/文献 API/コード生成委託など多数の外部通信を前提としており、そのままでは閉域で成立しない。

### 1.2 目的
1. 外部通信を一切行わずに論文生成パイプラインが完走できる「オフラインモード」を AutoResearchClaw に追加する。
2. 個人情報（PHI/ゲノム片/患者 ID 等）が LLM プロンプト、ログ、キャッシュ、生成物のいずれにも残留しないことを仕組みで保証する。
3. 本家 upstream (`aiming-lab/AutoResearchClaw`) への追従（`git rebase origin/main`）を続けられる構造で実装する。

### 1.3 非目的（やらないこと）
- 外部通信を"条件付きで許可"するハイブリッド運用（混乱と漏洩リスク源になるため不可）。
- ToMMo 以外の特定データセットへの個別最適化（汎用インタフェースを提供し、データセット別スキルで吸収する）。
- 閉域環境の構築そのもの（OS/ネットワーク/監査基盤は運用側で用意されている前提）。

#### 3.2.2 モデル候補（第一候補）

本件では Qwen 3.5 系（Apache 2.0）と Gemma 4 系（Apache 2.0）を組み合わせて役割分担する方針とする。両系列とも Apache 2.0 ライセンスであり、学術論文の成果物扱いで追加の法務確認は不要。

| 役割 | 第一候補モデル | 代替 | 備考 |
|---|---|---|---|
| Stage 17 執筆（日本語本文） | **Qwen3.5-122B-A10B** (MoE, アクティブ 10B) | Qwen3.5-35B-A3B | 多言語・長文執筆性能重視 |
| Stage 10 コード生成 | **Gemma 4 31B** (dense, 256k ctx) | Qwen3.5-27B / Coder 系 | LiveCodeBench v6 80.0% / Codeforces ELO 2150 |
| Stage 5/7/9 軽量 judge | **Gemma 4 26B A4B** (MoE, アクティブ 4B) | Qwen3.5-9B | ゲート判定・スキル選択 |
| 埋め込み | **intfloat/multilingual-e5-large** | bge-m3 | 生成系 LLM と分離 |

#### 3.2.3 VRAM プロファイル別構成

解析環境の GPU 予算に応じて以下 3 パターンから選択する。Phase 0 で実環境の VRAM を確認し、該当プロファイルを確定する。

| プロファイル | GPU 目安 | 執筆モデル | コード生成 | 軽量 judge | 想定論文生成時間 |
|---|---|---|---|---|---|
| **A: 潤沢** | A100 80GB / H100 / RTX 6000 Ada (48GB+) | Qwen3.5-122B-A10B | Gemma 4 31B | Gemma 4 26B A4B | 6〜12 時間 |
| **B: 標準** | RTX 4090 / 5090 (24〜32GB) | Qwen3.5-35B-A3B | Gemma 4 26B A4B | 同上を兼任 | 12〜24 時間 |
| **C: 最小** | RTX 4080 / A4000 (16GB) | Gemma 4 26B A4B（全役割兼任） | 同左 | 同左 | 24〜48 時間 |

> **MoE モデルの利点**: Qwen3.5-122B-A10B や Gemma 4 26B A4B はアクティブパラメータが小さく、推論速度はアクティブ量に近い。プロファイル B でも MoE 二枚看板なら同居しやすい。

#### 3.2.4 量子化・コンテキスト長

| 項目 | 仕様 |

| 量子化形式 | GGUF Q5_K_M（品質優先）/ Q4_K_M（VRAM 優先）/ GPTQ-Int4 / FP8 |

## 4. 機能要件

### 4.1 オフラインモード基盤（Phase 1）
- `runtime.offline_mode: bool` 設定フラグを導入。`true` の場合、外部通信を行うコードパスは実行前に短絡する。
- 起動時プリフライトで、`offline_mode=true` かつ外部 URL への DNS 解決/接続が発生した場合はパイプライン起動を拒否する。
- `pytest` で `socket` を監視し、オフラインモードで外向き接続が発生したら fail するテストを追加する。

### 4.2 LLM バックエンド（Phase 2）
- `llm.provider: "openai-compatible"` で Ollama / LM Studio を公式サポートする（設定サンプル `config.offline.yaml` を同梱）。
- Ollama の `num_ctx`・`keep_alive` 等をアダプタ経由で設定可能にする。
- コード生成委託 (`experiment.cli_agent.provider`) は `"llm"` に限定する。`codex` / `claude_code` はオフラインモードで使用不可として起動時に拒否する。
- PHI マスカー (`researchclaw/utils/redact_phi.py`) を LLM 入出力ロガーの前段に必ず挟む。マスク前ログはディスクに残さない。

### 4.3 埋め込み・ベクタ検索（Phase 3）
- 埋め込み呼び出しを `EmbeddingBackend` プロトコルとして抽象化。
- `LocalSentenceTransformersBackend` を追加し、事前持ち込み済みモデルを `models/embeddings/` から読み込む。
- ベクタストアは FAISS（または Chroma）にローカル永続。既存 KB (`docs/kb`) との整合を取る。

### 4.4 ローカル文献コーパス（Phase 4）
- `researchclaw/literature/local_corpus/` 配下に以下を追加する。
  - `ingest.py`: 学外 DMZ マシンで arXiv/OpenAlex/Semantic Scholar を巡回し、PDF + メタデータ + 埋め込み index を含むコーパスアーカイブを生成する CLI。
  - `corpus_client.py`: 既存 `LiteratureClient` インタフェース互換。BM25 + ベクトル検索のハイブリッド。
  - `pdf_store.py`: PDF 本文抽出を事前計算しキャッシュ。
- `literature/search.py` のディスパッチに `backend: "local_corpus"` を追加し、オフラインモードで強制選択する。
- `literature/verify.py` はオフラインモード時、ローカル index 内の DOI/arXiv ID 照合のみで存在確認を行い、未収録のものは `unverified` として HITL ゲートへ上げる（幻覚引用を通さない）。
- コーパス更新運用手順書を `docs/offline/corpus_update.md` に整備する。

### 4.5 実験実行環境（Phase 5）
- ゲノム解析用 Dockerfile を `researchclaw/experiment/docker/offline/` に追加し、必要ツール（bcftools / plink2 / samtools / GATK / scikit-allel / nilearn 等）を事前ビルドする。
- `experiment.docker.network_policy: "none"`、`auto_install_deps: false` をオフラインモードの既定とする。
- `pip` 依存は事前構築した wheelhouse から `--no-index --find-links` で解決するヘルパーを追加する。
- データディレクトリは read-only マウント。出力は独立ボリュームに限定する。
- Stage 10（コード生成）のプロンプトに「利用可能ライブラリ一覧」「ネットワーク不可」「データパス固定」を注入する `offline_context.py` を追加する。

### 4.6 ドメインスキル（Phase 6）
- `skills/builtin/domain/genomics-wgs/SKILL.md`: VCF/BCF ハンドリング、GWAS/PRS、集団遺伝学の定型手順。
- `skills/builtin/domain/tommo-cohort/SKILL.md`: dbTMM データ辞書の参照方法、三世代コホートのファミリー構造、小セル集計など禁止事項の NG リスト。
- Stage 7 / 10 / 13 / 17 のスキルピッカでオフラインモード時に優先選択されるようタグ付けする。

### 4.7 HITL・監査（Phase 7）
- `HITLConfig.pii_gate_stages` を新設し、Stage 13 実行前 / Stage 17 執筆前 / Stage 20 公開前を `FULL_AUTO` でも迂回不可の強制ゲートとする。
- 全 LLM 入出力を PHI マスカー通過後に `logs/audit/<run_id>/*.jsonl` として保存する。マスク前データは永続化しない。
- `cli_adapter.py` に「個人情報チェック」アクション（キー `p`）を追加し、レビュー者が明示承認しないと次 stage へ進めないようにする。
- 監査ログは改竄検出のため直前レコードのハッシュを各行に含める（hash chain）。

## 5. 非機能要件

### 5.1 セキュリティ
- オフラインモード時、AutoResearchClaw プロセスから外向きに発生する TCP/UDP 接続は**ゼロ**であること（`nftables`/`iptables` レベルで検証可能）。
- LLM プロンプト、キャッシュ、ログ、生成物のいずれにも、PHI マスカー未通過のデータを残さないこと。
- 設定ファイル・コード内に API キーやエンドポイントを誤ってハードコードしていないことを CI で検査する。

### 5.2 監査性
- 各 stage の開始・終了、HITL 承認、LLM 呼び出し、データ読み取り、成果物出力を時系列で追跡可能であること。
- 監査ログは単一ファイルに追記のみで、改竄検出が可能な形式であること。
- `run_id` 単位で全生成物・ログをアーカイブできること。

### 5.3 再現性
- 同一入力・同一モデル・同一シードで、パイプラインの出力が概ね再現可能であること。
- LLM モデルのバージョン、埋め込みモデルのバージョン、Docker イメージのハッシュを成果物メタデータに記録する。

### 5.4 パフォーマンス
- 論文 1 本あたりの生成時間は運用で許容される範囲（目安として 1 日以内）。
- ローカル LLM の VRAM/RAM 要件は事前に把握し、Phase 0 の環境調査で上限を見積もる。

### 5.5 保守性
- 既存 v0.4.0 のディレクトリ構造・ステージ定義を壊さない。オフライン対応は追加ファイル・設定フラグ・アダプタ差し替えで実現する。
- `git rebase origin/main` が継続可能であること。

---

## 6. 制約・前提

- ローカル LLM の品質は、執筆タスクで最低 30B 級、理想は 70B 級の量子化モデルを想定する。
- 文献コーパスは学外 DMZ で月次程度で更新する前提。閉域内での最新研究参照性は運用で補う。
- 解析環境内での LLM 利用可否は運用側が規程・IRB に基づき事前承認していることを前提とする。

## 7. リスクと対応方針

| リスク | 影響 | 対応 |
|---|---|---|
| 規程上 LLM 利用が不可 | プロジェクト成立不可 | Phase 0 で文書確認。不可なら中止判断。 |
| ローカル LLM の執筆品質不足 | 論文品質低下 | 執筆 stage のみ人手比率を上げる / より大きいモデルへ差し替え。 |
| 文献コーパスの鮮度不足 | 最新研究比較が弱くなる | コーパス更新頻度を運用で担保。 |
| PHI マスカーの漏れ | 重大インシデント | 正規表現 + 語彙 + 単体テスト + ランダムサンプル人手レビュー。 |
| 監査ログの改竄 | コンプライアンス違反 | hash chain と WORM ストレージへの書き出し。 |
| Upstream との衝突 | 保守負荷増 | アダプタ/プラグイン形式で実装し、本体ファイル改変を最小化。 |

## 8. 受け入れ基準（Phase 8 E2E）

- [ ] `nftables`/`iptables` で外向き通信を遮断した閉域再現環境でパイプラインが完走する。
- [ ] 1000 Genomes など公開ダミーデータを用いた WGS 比較解析のトピックで論文 1 本が生成される。
- [ ] 生成された論文・図表・監査ログ一式がレビュー観点（引用の実在性、PHI 非残留、統計手法の妥当性）を満たす。
- [ ] 監査ログが hash chain を含み、改竄検出テストが通る。
- [ ] オフラインモード違反検知テスト（`socket` 監視）が通る。
